F1C200S 投屏优化记录
记录日期：2026-10-01
范围：本轮 800×480 硬解旋转投屏、蓝牙音频、ADB 自动连接测试及性能优化。
说明：本文依据已保存的源码提交、构建哈希、板端日志和对照采样整理。不同阶段的数据不能拼成同一次运行；没有证据的原因不作确定结论。

一、当前结论

1. 本轮频繁卡顿的重要来源是板端处理开销和本机 UDP 接收队列溢出，不应把所有缺包都归咎于无线链路或 AIC 驱动。
2. 最有效的两项性能优化是：有界批量接收 RTP，以及小延迟、有上限的 FIFO 合并写出。
3. 丢包后请求关键帧能缩短恢复时间，但不能替代接收性能优化；单独增加 IDR 请求并没有消除本机溢出。
4. 优化后已有约 35 分钟的连续播放记录：没有秒级停顿，最长成功显示提交间隔约 252 毫秒。但这不等于绝对无卡顿，也不等于完整稳定版本已经验收。
5. 最新一轮采样中约 20 万个 RTP 包没有序号缺失，本机 socket 溢出为 0；音视频数据持续处理，用户也反馈效果很好。
6. 端到端延迟还没有准确实测。三次完整冷启动验收尚未完成；不应提前推送“稳定版”或宣称全部问题都已解决。

二、需要始终保护的链路和约束

视频链路：
手机 RTP/MPEG-TS → sink 提取 PES 中的 Annex-B H.264 → 有界 RAM 输出队列 → /tmp/aic_h264_live.fifo → Cedar 硬解播放器 → 90 度旋转后的 480×800 原生显示。

音频链路：
手机 MPEG-TS 中的 LPCM → 解包、转换及有界 PCM 队列 → ALSA default → BlueALSA → 蓝牙音响。

重要约束：
  - /tmp/aic_h264_live.fifo 是命名管道，不是视频文件。数据经过内核 pipe buffer，不把整段 H.264 缓存到磁盘。
  - 视频输出队列固定 128 KiB，工作线程临时块 4 KiB、栈 64 KiB；不允许无界积累。
  - 不能随机丢弃 H.264 字节“减负”，否则会损坏帧结构和参考帧链。队列满必须明确报错。
  - 保留 800×480 输入、Cedar 硬解、90 度旋转、480×800 原生输出。不以缩小画面、缩放裁剪或降低规格代替优化。
  - RTL8723BS 负责普通联网和 SSH，AIC8800 只负责投屏；不恢复 8723BU 开机加载。
  - 手机横屏、视频和循环播放由用户设置。ADB 只操作投屏连接、断开和返回原媒体任务。
  - 本轮接收性能对照保持 kernel 5.7.1 #250、现用驱动、DTB、CMA 总量和显示路径不变，不替换旧归档驱动。
  - 在原源码工作树建立候选分支，不新开工作树。源码先提交 Git，再部署独立候选，中文变更记录同步更新。

三、查到的问题、解决办法和验证结果

问题 1：CPU 忙不等于正在有效解码，空闲解码循环也会消耗大量 CPU

现象与证据：
  原播放器每轮解码后固定 usleep(50)，缺少码流时仍然频繁醒来继续调用解码器。
  采样中解码线程曾约占 21% CPU，主动切换约 1758 次/秒。
  一组返回码统计中约 91% 是 NO_BITSTREAM，说明大量调用实际上没有有效输入。

处理：
  去掉每轮固定 50 微秒的等待；仅在 NO_BITSTREAM 或 NO_FRAME_BUFFER 时等待 2000 微秒再检查。
  有效解码、PTS、原生显示和帧率节奏保持原样。
  增加解码返回码汇总，以及主程序退出原因记录。

结果与边界：
  较早对照中解码线程约降到 5%，主动切换约 295～373 次/秒。
  这不是解码线程以后永远只占 5%：后续 800×480 内容和负载不同，实际 CPU 会变化。
  解码空闲开销减少了，但本机 UDP 丢包仍存在，不能把此项单独称为完整修复。

问题 2：RTP 缺包发生在本机接收队列，而非都发生在空中

现象与证据：
  CPU 曾长期处于约 90%～97% 忙碌状态。
  接收器统计 RTP 序号缺失，同时读取 SO_RXQ_OVFL，并检查 /proc/net/udp 对应 socket 的 drops。
  多组记录里 missing 与 socket_missing 完全对应，例如同为 13483；该阶段重复包、乱序包为 0。
  FIFO 队列没有满，written 与 submitted 能追平，说明不是无限视频队列堆积。

结论：
  这些观察段中的 RTP 序号缺失能够由本机 socket 溢出解释。
  无线网络看起来稳定，也可能因为程序取包不够及时而掉包。
  这不能推广为“无线底层永远没有丢包或重传”；没有测到的无线指标不能臆测为 0。

处理：
  先补接收间隔、写出耗时、socket drops 和有界队列统计，再针对系统调用和线程唤醒优化。
  曾使用 socket 局部 SO_RCVBUF 请求 180224 字节，Linux 返回有效值 360448 字节。
  不改全局 sysctl。增大接收窗口只能吸收短时处理迟滞，不能解决持续 CPU 过载，还可能增加排队延迟。

问题 3：同步写 FIFO 会让收包线程承担播放器背压

处理过程：
  先把同一个 RTP 包内的多次 H.264 小写合成一次，保证提取字节不变；测试案例中 6 次写变成 1 次。
  再把视频输出交给独立工作线程，使用固定 128 KiB RAM 环形队列、4 KiB 写出块和非阻塞 write/poll。
  保留 FIFO 的实时流方式，不改成“先存文件，再播放”。

验证：
  精确字节、环形回绕、EPIPE、停止、队列满等测试通过。
  实际视频队列 full=0，submitted 与 written 能追平；不持续积压。

边界：
  收包与写出分离有价值，但单独加入异步队列还没有消除频繁丢包。
  线程和锁本身也有开销，不能把“异步”当成自动更快。

问题 4：丢包后 H.264 参考帧损坏，画面需要关键帧恢复

处理：
  检测 RTP 前向序号缺失和 socket 溢出，设置待恢复状态。
  使用 WFD_LOSS_IDR=1 请求新的 IDR；追加恢复请求最多每秒一次，首次 IDR 也计入冷却时间。
  重复包、旧包不回退高水位；处理 16 位 RTP 序号回绕、SSRC 切换及溢出计数回绕。

验证：
  真机对恢复请求返回 RTSP 200 OK；纯状态机及模拟 RTSP 测试覆盖回绕、重复、乱序、限速等情况。
  同一诊断播放器的早期对照：
    开启追加 IDR：125.25 秒，最长显示提交间隔约 1.27 秒。
    关闭追加 IDR：130.28 秒，最长间隔约 3.98 秒。
  关闭后 CPU 或丢包数字可能下降，但长时间画面停顿反而更严重，所以保留恢复请求。

边界：
  200 OK 只证明请求被协议端接受，不等于一定已经解码、显示了新关键帧。
  IDR 请求会增加关键帧处理负担；应限速，不应每发现一个缺包就发请求。
  IDR 是恢复机制，不是本机接收溢出的根治办法。

问题 5：每个 RTP 包都 select + recvmsg，接收调用过于频繁

处理：
  WFD_RTP_BATCH=1 时使用 recvmmsg，每次最多取 16 个已经到达的 UDP 报文。
  使用非阻塞方式，不等待凑满 16 个。处理完有限批次就返回 RTSP 检查，避免控制消息被无限取包循环饿死。
  每个报文保留独立的 SO_RXQ_OVFL 控制信息；重复使用槽位前重置长度和标志。
  拒绝截断的超长报文；内核不支持 recvmmsg 时回退到逐包接收。
  固定接收存储约 34 KiB，不新增线程或无界队列。

验证与数据：
  UDP 顺序、空队列、零长度、截断、槽位重用、回退路径及原字节等价测试通过。
  800 格式 RTSP 协商和 IDR 测试通过，两次 ARM 构建哈希一致。
  真机平均每次接收约 13 个报文；没有触发回退或截断。
  对照记录：
    旧接收器：636.24 秒，106 次间隔超过 250 毫秒，最长约 1.78 秒。
    批量第一轮：170.32 秒，0 次超过 250 毫秒，最长约 201 毫秒。
    批量重连第二轮：210.47 秒，1 次超过 250 毫秒，最长约 1.08 秒。
  接收线程 CPU 从较早约 17%～18% 降到约 11%～13%。
  两轮各六个采样窗口的新增本机丢包分别为 34/0/0/4/0/0 和 55/8/0/28/0/1。

边界：
  不同视频阶段和时长未严格逐帧对齐，不能据此计算一个准确的总体提升百分比。
  批量接收改善明显，但第二轮仍有一次秒级停顿，不能单独宣布问题完全解决。

问题 6：FIFO 工作线程仍然每个小包被唤醒，IPC 开销偏高

现象：
  批量接收之后，FIFO 工作线程仍约有每秒 600～800 次主动切换，CPU 约 8%～10%。
  主线程每次小数据提交都发条件变量通知，工作线程频繁写入，播放器读线程也频繁被唤醒。

处理：
  WFD_VIDEO_COALESCE=1 时，积累到 4096 字节立即写出。
  不足 4096 字节时，最多主动等待 3 毫秒，用 CLOCK_MONOTONIC 和固定截止时间；虚假唤醒不会重新计时。
  仅在空队列收到数据、跨过 4 KiB 门槛、错误或停止时通知工作线程，不再每个小追加都通知。
  原队列容量、临时块、线程栈保持不变，不增加视频缓存。
  增加实际成功写次数、通知次数和合并等待块统计。

验证：
  开启、关闭两种状态下，原 20 轮生命周期、队列满、EPIPE、字节一致性测试通过 ASan/UBSan。
  新增短尾包定时写出、50 轮停止、4 KiB 整块不进入等待等测试通过。
  测试读取数据后要等待写线程记账完成，避免“读完了，但 written 计数尚未更新”的测试竞态。
  50940 次 RTP 视频提交，在一个观察点合成了 18705 次实际成功 FIFO 写出。

同一二进制开关对照：
  开启第一轮：240.45 秒，无超过 250 毫秒的提交间隔，最长约 157 毫秒。
  关闭对照：CPU 约 93%～95%，FIFO 主动切换约 738～820 次/秒；已观察到约 733 毫秒的提交间隔。
  恢复开启第二轮：210.32 秒，无超过 250 毫秒的提交间隔，最长约 121 毫秒。
  开启后的 FIFO 主动切换约 276～341 次/秒，工作线程 CPU 约 5%～7%。
  恢复开启后的六个采样窗口没有新增本机丢包，CPU 约 81%～87%，蓝牙 PCM 持续写入。

边界：
  3 毫秒是主动合并等待上限，不保证包括线程调度、pipe、解码和显示在内的总延迟也只有 3 毫秒。
  队列中暂留几百字节的尾包不是丢弃，应看后续 written 是否追上 submitted。
  开启后实际提交率随源内容变化，不能把某个阶段的较高帧率全部归因于合并。

问题 7：蓝牙“已连接”不代表音频传输真的工作

现象与证据：
  曾有三次新会话只写出很少 PCM 就停止，出现 ALSA EPIPE/ENODEV。
  当时 BlueZ 仍显示 Connected，PCM 端点也可见，HCI 错误计数为 0。
  BlueALSA 日志却有 BT socket write timeout 和释放 transport 时的 UnknownObject。
  音频失效后 CPU 和丢包数字变好，容易误以为视频优化有效。

处理与结果：
  单纯断开重连音响、重启 BlueALSA 曾不足以恢复。
  标准 hci0 down/up 后重连音响，恢复了持续音频传输。
  使用一致的 HCI 初始化条件重新做完整音视频对照；失效音频的那组数据明确标为无效。
  后续批量接收和 FIFO 合并的多个重连测试，蓝牙 PCM 持续增长，没有再次依赖 HCI 重置。

未解决部分：
  需要重置 HCI 的最底层原因还没有确定，不能直接断言是 UART、固件或硬件损坏。
  Connected、端点存在、单次 HCI errors=0 均不足以证明可听声音正常。
  必须检查 PCM 写入是否持续，结合 HCI 发送、后端错误和实际听音验证。

问题 8：日志警告和程序存活可能造成错误判断

处理：
  在成功接受视频显示提交的 ioctl 后记录单调时钟间隔，每 5 秒汇总一次。
  统计提交次数、超过 50/100/250 毫秒的次数、最大间隔、当前未更新时间和提交错误数。
  汇总时保留开始出帧之后的零帧窗口，不能把完整停顿窗口删掉，让统计看起来更好。

学到的区别：
  raw H.264 播放器使用合成的 60fps PTS，源画面更新节奏可能变化；video clock late 不是画面实际冻结时长。
  程序活着、FIFO 字节增加，只证明部分链路工作，不证明屏幕持续更新。
  成功显示提交比单纯进程存活更有价值，但仍不等于物理屏幕实际扫描或画面内容变化的最终证明。
  屏幕扫描约 60 Hz，不表示每秒一定有 60 个不同的视频画面。最近实际视频提交约 40～45 次/秒，其他阶段曾约 43～51 次/秒。
  RTP 缺包率、音频队列丢弃率、显示帧间隔、端到端延迟是不同指标，不能混用。

问题 9：自动重连和采集工具自身也会出错

ADB：
  本机原生 adb CLI 曾因环境中的 .android 路径问题崩溃，但已有授权的 ADB server 能使用。
  主机工具通过已有 server 的 transport/shell 协议操作手机，不为此反复安装或重建环境。
  动态解析 CAST_SETTINGS 的 UI XML，匹配启用的 F1C200S-AIC，使用当前控件边界，不盲点旧坐标。
  连接成功后返回原媒体任务，并只读确认 Bilibili 在前台、MediaSession 为播放状态。

重连时序：
  手机显示已断开时，旧 sink、播放器和 watcher 可能仍未完全退出。
  必须等待旧进程终止，并检查上一条命令返回码，再启动或连接；不能在失败后继续连锁执行下一步。
  观察超时不等于进程死了，更不能因此直接重启正在播放的会话。
  板端 PID 曾回绕，新的小 PID 不证明板子重启；是否重启要检查 boot ID 和 uptime。

日志采集：
  有一份仍在增长的播放器日志通过 PSCP 传输时触发断言，目标文件为 0 字节。
  该组完整播放器统计缺失，不能补算、伪造或沿用其他组的数据。
  后续先冻结小文本诊断日志快照，SSH 传输后清除远端临时快照；这不是保存视频或复制系统备份。

冷启动：
  已重新写出当前链路的启动脚本，包括哈希预检、5GHz GO、自动 PBC、DHCP、蓝牙默认路由、播放器和三个优化开关。
  热重连验证成功；cold 模式拒绝覆盖已有运行目录；/tmp 是 tmpfs，断电后运行目录会消失。
  当前映射为 COM3 电源、COM4 板端控制台，不能照搬技能里旧的 COM5/COM6。
  一次电源切换得到了 OFF/ON 确认，boot ID 确实变化，SSH 和默认蓝牙恢复。
  但 COM4 采集在上电后报句柄读取错误，整轮不能算完成。重新打开串口可以无异常读取，但当时没有采到启动文本。
  上电后重新打开并验证串口采集的工具修复仍待完成；不能把此问题直接归咎于板子或接触不良。
  随后当前冷模式启动脚本已在新 boot 上成功注册 wlan1、重建 GO 并启动播放器；最新采样确认投屏已连接。

四、内存方面的认识和限制

1. CMA 是连续物理内存区域，不是“总 RAM 外又多出来的 24 MiB”，不能和 MemAvailable 相加。
2. MemFree、MemAvailable、CMA 空闲、进程 RSS、slab 统计不是同一口径。
3. CMA 空闲变化不能单独证明播放器泄漏，必须结合实际分配、释放、普通内存和重复会话趋势。
4. 此前已做过虚拟摄像头/测试声卡和显示缓存的内存整理；本轮主要性能对照不再改内核或 CMA 总量。
5. 播放器使用可选私有连续 CMA 池，将解码相关小分配集中到一个 arena。本轮 800×480 配置为 9 MiB。
6. 私有池仍要保留正确的物理地址、缓存操作及必要回退，不能用缩减参考帧/VBV 或破坏对齐代替内存优化。
7. 初始化解码器可能重新设置 memops，不能只改调用者传入的配置指针就假定自定义分配器已生效。
8. 不要为得到好看的 CPU 或 RAM 数字关闭蓝牙音频、缩小视频或换成静态设置页，再宣称完整投屏改善。

最近一次已报告的采样口径：
  Linux MemTotal 约 52.8 MiB，最新 MemAvailable 约 19.0 MiB。
  按这两个值相减约 33.8 MiB 暂不可用，但这不是所有进程 RSS 的总和。
  CMA 总计 24 MiB，其中空闲约 10.4 MiB，已包含在上述 RAM 中。
  CPU 约 82%～86%，实际视频提交最近约 40～45 次/秒，VSync 等待频率约 60～61 次/秒。
  本轮约 20 万个 RTP 包，序号缺失 0、本机溢出 0；不代表无线底层重传一定为 0。
  音频 PCM 队列累计丢弃约 0.57%，不是 RTP 网络丢包率。
  本轮最长已完成显示提交间隔约 168 毫秒，不是手机到屏幕的端到端延迟。

六、以后继续开发时应遵循的办法

1. 先看实际运行的可执行文件哈希、配置、boot ID、进程和音频数据，再决定修改哪里。
2. 一次只验证一个明确假设；控制分辨率、旋转、音频、网络和播放器一致。
3. 先测真实瓶颈：CPU 分线程、系统调用/唤醒频率、RTP 序号、socket 溢出、FIFO 队列、实际显示间隔。
4. 不拿进程存活、RTSP 200 OK、静态画面或“Connected=true”代替完整功能验证。
5. 每条数据都带观察阶段和口径。早期最大间隔不是整个后续会话最大值；失效日志不能算有效样本。
6. 稳定低延迟的关键不是无限增大缓冲，而是减少每个包的固定开销、避免无谓唤醒，同时保持等待和队列有界。
7. 恢复机制与性能机制分开：IDR 用于参考帧恢复，批量接收/FIFO 合并用于降低本机开销。
8. 视频字节完整性优先；音频队列丢弃要单独记录，不能隐藏为“网络无丢包所以全部正常”。
9. 修改前必须能复现当前产物，保留匹配源码、配置、依赖和回退入口。连续两次构建哈希一致是必要证据之一，不是最终验收。
10. 只在原工作树改源码并提交 Git，及时写中文变更记录。不新建未授权工作树、不随意换旧驱动、不乱推稳定归档。
11. 串口只做控制、启动观察和恢复；板端文件通过 SSH 传输。工具如需安装，放到 D:\AI工具。
12. 自动测试不能自动编造成功；返回码、进程终止、数据持续增长和失败原因都要明确核对。
